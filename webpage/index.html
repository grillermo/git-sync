Commit on one machine.It's already on the others.

git-sync keeps a chosen set of git repos in step across every machine you work on. Commit anywhere in the mesh and the commit is on the rest of it seconds later — no stashing, no pulling, nothing to remember. Your own git remote carries the code; SSH carries one sentence: there is something to pull.

The problem

Two machines, one brain, and a dance you do twenty times a day

If you work on a desktop and a laptop — or a Mac and a Linux box, or a machine at home and one at the office — git already solves the hard part. What it does not solve is the clerical part, and the clerical part is the one that bites.

"Which one has it?"

You sit down at the other machine and the first thing you do is try to remember whether the work you are thinking of lives here or over there.

You forgot to push

The fix is committed. On the machine you are not sitting at. You find out an hour into re-doing it, or worse, after you have made a second, different fix.

Stash, pull, pop, repeat

Switching machines means a dirty tree, a pull that will not fast-forward, and a stash you have to remember to pop. Every single time.

Code arrives, nothing restarts

Even once the commit is there, the service on that machine is still running the old build until you go and rebuild it by hand.

What git-sync removes

The step. Not the git. There is no daemon watching your files, no proprietary sync protocol, no copy of your code on someone else's server. A commit is still a commit, pushed to the remote you already use, and the other machines simply fast-forward onto it without being asked.

What it refuses to do

It never commits for you, never pushes on your behalf from a machine you were not sitting at, and never merges anything that is not a fast-forward. Genuinely diverged history is reported and left alone, because that one is yours to think about.

How it works

The remote is the transport. SSH is just the doorbell.

Every machine in the mesh already pushes to, and pulls from, the same git remote. git-sync does not invent a new channel for your code — it reuses that one. The only thing that travels machine to machine is a notification.

You commit

A global post-commit hook fires in every repo on the machine, but only acts on the ones you ticked. It does almost nothing itself — git is waiting on it — and re-execs detached so your prompt comes straight back.

It pushes the branch

To the repo's shared remote, resolved by name the same way on every machine: github if there is one, else origin, else the repo's only remote. Never the branch's upstream, so two machines can never disagree about where they meet.

It rings every other machine, in parallel

One SSH command per peer, key-only, carrying the repo's relative path and nothing else. A machine that is asleep or off is not an error — the delivery is queued.

They fetch and fast-forward

Each peer takes a per-repo lock, fetches that same remote, stashes if the tree is dirty, fast-forwards, and unstashes — always, whether or not the fast-forward worked, so a stashed tree is never silently lost.

And, if you asked, they run ./activate

Only the machines that received the change run it, one repo at a time, so the thing you just changed is rebuilt and restarted where it runs.

A repo mid-sync refuses commits

While a machine is fast-forwarding a repo, that repo's pre-commit and pre-push hooks refuse — naming the machine that is mid-sync — so a commit can never be made, and broadcast out, from under a merge.

And the lock fails open

A receive that dies — killed process, closed lid — leaves a lock that goes stale on its own after five minutes. git-sync unlock clears one by hand. A wedged lock can never permanently stop a repo from taking commits.

Nothing in the path can prompt you

The hook and its children run detached, with no terminal. That is why SSH is key-only everywhere, with no password fallback: there is no one there to answer.

Setting it up

Type on one machine. The rest provision themselves.

You run install once, on any one machine, naming the others. It connects, lets you pick repos, verifies what it found, and then sets up every machine in the mesh over SSH — binary, config, hooks and login service. Nothing is typed on any of the others.

The connect stage probes every ordered pair of machines in the mesh, not just this one to each peer — a key missing between two peers would otherwise only surface later as a failing notification nobody is watching. Each failure is named for what it actually is (host key never seen, host key changed, key rejected, sshd off, name does not resolve) and comes with the exact command that fixes that pair, on the right machine. On a terminal, install offers to run them for you. The rest of the mesh is set up either way.

The pick stage: sync is opt-in per repo, and each row names the remote that repo would actually sync through — so a repo with no remote, which cannot sync at all, says so before you tick it. Type to filter. Then the verify stage asks every reachable machine which of those repos it really has, and whether its clone points at the same remote, because a one-sided or differently-remoted repo would otherwise never converge and never say why.

Features

Everything it does

Thirteen subcommands off one binary; six of them are for you and the rest are what the machines say to each other.

Opt-in, per repo

A repo that is not on the allowlist is a silent no-op everywhere — hook, push and receive alike. Syncing is a property of a repo, not of a machine.

Any number of machines

Not a pair. A mesh: every machine notifies every other in parallel, and each one gets its own view of the peer list written for it during install.

Finds machines on your network

With no peers named, install browses Bonjour for _ssh._tcp and sweeps port 22 across your /24 for about six seconds, and lists what it finds in a checkbox picker as they turn up. Discovery only suggests — every machine you tick still goes through the key-only connect check.

Offline machines catch up

A push or notify that failed only because something was unreachable is recorded as offline, not as an error, and queued. Every later push retries the backlog, and being notified at all proves this machine is back online, so it drains then too.

Wakes up with your laptop

A LaunchAgent on macOS, a systemd user unit on Linux. It announces at login and again on every wake from sleep — detected by comparing the monotonic clock, which stops while the machine sleeps, against the wall clock, which does not.

Catches up from the remote too

On announce, every selected repo is brought forward from the shared remote directly — so a commit whose author machine is now switched off is still picked up.

./activate: make it live

Drop an executable ./activate at a repo's root and git-sync runs it after a sync moves that repo forward — rebuild, restart, whatever "deploy" means there. Only receiving machines run it, never the one that committed.

One activate at a time

Runs are queued per repo (three quick commits make one run, with the oldest revision as GITSYNC_OLD_REV) and drained serially per machine. The repo is locked while its script runs, so nothing rewrites the tree under a build.

Levels the machines at install

One unpushed commit sitting on any machine would make every later sync warn instead of apply, forever. So install measures each machine against the remote and pushes whichever side is purely ahead, fast-forwarding whichever is purely behind — using nothing but push and merge --ff-only.

Clones what a peer is missing

A selected repo that verify finds absent on a peer is cloned there during install, from the same remote URL under the same remote name — never over an existing path, never with a prompt. --no-clone skips it.

An activity log you can read

Every push, notify, receive and activate is a line in an append-only JSON log, kept short enough that concurrent writes from separate processes cannot interleave. No lock, no database, greppable.

git-sync report

A terminal browser over that log, grouped by repo, with --since, --repo and --errors filters. Pipe it and you get static, greppable text instead of the TUI.

A menu bar app for the Mac

The icon turns while anything is syncing and gets a red dot when a repo has a problem. It reads nothing but git-sync status --json --follow.

Key-only SSH, by design

BatchMode=yes everywhere, with keepalives so a peer that vanishes mid-receive becomes an exit code in about a minute rather than a hung background push. There is no password path to fall back to, and nothing that could ask.

Honest about one-sided repos

A repo that exists on only one machine, or that was cloned from a different remote than the peer's copy, is a warning you can see — never a silent drop, never an automatic clone behind your back, never a retry loop.

Mesh-wide uninstall

git-sync uninstall SSHes every machine to remove itself, keeping each one's history. --purge takes the config and activity log too; --local limits either to the machine you are sitting at.

It behaves like your git

Every git operation shells out to the real git binary, never a library — so your credential helpers, your config, your hooks and your SSH setup all apply exactly as they do when you type it yourself.

Nothing leaves your machines

No account, no server, no telemetry. The only third party involved is the git remote you were already pushing to.

macOS menu bar app

Is everything in step right now?

A small accessory app that answers that without you asking. The icon turns while git-sync is working, and carries a red dot whenever any repo has a problem — a rejected push, diverged history, a failed ./activate.

Click the icon for one row per synced repo — state, the machine a delivery is bound for, when it last synced, and what happened. Clicking a row copies that repo's path. The app reads one thing and nothing else: git-sync status --json --follow.

Who it's for

The ideal user owns more than one computer and resents it slightly

This is for you if

  • You work on two or more machines you control. A desktop and a laptop, a Mac and a Linux box, a machine at home and one at the office — and you move between them during a single piece of work.
  • Your repos are already on a remote you push to. GitHub, a self-hosted Forgejo, a bare repo on a NAS. git-sync needs a shared remote; it does not care which.
  • They are all on one network, or at least reachable by SSH. Key-only, every machine to every other.
  • You have a dotfiles, notes or scripts repo you commit to constantly and resent having to push and pull by hand.
  • You run something on one of those machines — a server, a cron job, a menu bar app — and want a commit to rebuild and restart it there.
  • You would rather self-host it than hand a folder of source code to a sync service.

This is not for you if

  • You want file sync. git-sync moves commits, not working trees. Uncommitted work stays where you made it — that is the point, not a gap.
  • You want a backup. It fast-forwards; it never keeps a copy of anything your remote does not already have.
  • You collaborate with other people on these repos. It is built for one person's several machines. Nothing breaks with teammates, but nothing in it helps with them either.
  • You keep different branches checked out per machine. Then there is usually nothing to fast-forward, which is normal and not an error, but also not much use.
  • Your repos rely on repo-local hooks. git's core.hooksPath is global and exclusive: installing git-sync means Husky or the pre-commit tool no longer runs on its own, and must be invoked from git-sync's shim.
Install

Once, on one machine

install 
# get the source — you need Go 1.26 and nothing else
$ git clone https://github.com/grillermo/git-sync.git
$ cd git-sync

# build the binaries for every platform in the mesh
$ ./build

# then, from one machine, name the others
$ bin/git-sync install ~/code \
      --peer you@laptop.local \
      --peer you@linux-box.local

# or name none, and let it scan the network for them
$ bin/git-sync install ~/code

What you need

SSH by key from every machine to every other. The same repos cloned at the same path relative to each machine's base directory, from the same remote. Push access to that remote everywhere. macOS or Linux, arm64 or amd64.

What it writes

A ~/.gitsync directory per machine — the binary the hooks invoke, three hook shims, a config file, the activity log — and git's global core.hooksPath, pointed at those shims.

Adding one repo later

Run git-sync install with no base directory from inside the repo. No scan, no repo picker; it keeps the existing install and just adds that one.

The commands you'll actually type

CommandWhat it does
git-sync install <dir>Set up the whole mesh from here: connect, pick, verify, install.
git-sync reportBrowse sync activity, grouped by repo. --since, --repo, --errors, --plain.
git-sync activate [repo]Run that repo's ./activate now, in the foreground, with output on your terminal.
git-sync unlock [repo]Clear a sync lock by hand, if a receive died and you would rather not wait out the stale timeout.
git-sync service installInstall or replace the login service on every machine in the mesh (--local for just this one).
git-sync uninstallRemove git-sync from every machine. --purge takes config and history too; --local stays here.

Seven more subcommands exist and are hidden from -h on purpose: they are what the machines invoke on each other.

Fork it

It's open source, under the GNU AGPL v3.0. Use it, change it, run your own mesh on your own fork — none of that needs asking.

fork, change, check 
# fork on github.com/grillermo/git-sync, then
$ git clone git@github.com:<you>/git-sync.git && cd git-sync

# everything runs through plain go test — no external runner
$ make check          # go vet + gofmt + go test ./...
$ go test -race ./...  # the concurrent paths

# then build and install your own copy over the mesh
$ ./build && bin/git-sync install ~/code --peer you@other-machine

Every test that touches the filesystem or git goes through a sandbox that points HOME, GITSYNC_HOME and git's global config at a temp tree, so running the suite can never reach your real ~/.gitsync. Pull requests welcome; issues too.
